# Разработка TravelTech

Работаем в приватном репозитории. Каждую задачу делаем в отдельной ветке, а изменения в `main` отправляем через Pull Request.

```bash
git switch main
git pull --ff-only
git switch -c fix/short-description
```

Перед изменением поведения добавь тест, который воспроизводит проблему. Не смешивай в одном PR исправление логики с форматированием десятков других файлов.

## Проверки

Один раз установи зависимости:

```bash
python -m pip install -r requirements-dev.txt
```

Перед PR выполни:

```bash
python scripts/check_local.py
git diff --check
```

Если меняешь большие участки, дополнительно запусти `python scripts/check_local.py --suite full`. Для браузерных проверок используется `python scripts/check_local.py --suite browser`. Нужны Microsoft Edge и Playwright. После изменений в API LiteAPI протестируй отдельный запрос в sandbox.

Облачных сборок нет. Поэтому в описании PR укажи запущенные команды, результаты и то, что не удалось проверить.

## Как писать код

Имена функций и переменных должны объяснять назначение. Комментарии нужны там, где важно понять причину проверки или необычное поведение, а не для пересказа каждой строки.

Не выдумывай отсутствующие параметры поездки. До сохранения пользователь должен подтвердить условия. Данные LiteAPI sandbox не считай подтверждёнными ценами или доступными к бронированию номерами.

В `experimental/` находится рабочий код и часть исследовательских компонентов. `audit/`, `research/` и `vendor/` пока не переносим. Внешние файлы могут использовать существующие пути. Подробнее: [карта кода](docs/CODE_GUIDE.md).

Для Python настроен Ruff с длиной строки 100 символов. Старые файлы пока отформатированы не одинаково. Не переоформляй их целиком, если твоя задача не связана с форматированием.

## Pull Request

Опиши исходную проблему, что исправил и как воспроизвёл результат. Если затронул интерфейс, приложи обезличенный скриншот. Тестовый ключ, данные сессий и реальные журналы не публикуй. Другие правила работы с данными есть в [SECURITY.md](SECURITY.md).

## Привязка задачи к официальным требованиям

Перед реализацией Issue и отправкой PR прочитайте [конкурсную базу](docs/hackathon/2026-10-24/README.md). Для изменения, связанного с хакатоном, укажите в PR:
- ID требований (Fxx/Txx/Oxx), ID gap (Gxx) и связанные сценарии приёмки (Axx) по [карте следимости](docs/hackathon/2026-10-24/data/traceability.json);
- ссылку на исходное ТЗ [S01/S02](docs/hackathon/2026-10-24/sources/README.md);
- что именно проверено на каком commit и что осталось `not_run`;
- при изменении условий интеграции — тип данных LIVE/SANDBOX/CACHED/MOCK и точный источник.

Прежде чем реализовать новый API-контракт или менять слой общих данных, согласуйте краткий ADR с участниками. Черновик [архитектуры](docs/hackathon/2026-10-24/09_ARCHITECTURE_PROVIDERS_KICKOFF.md) не является уже утверждённым решением.

## Архитектурные изменения

Изменения HTTP, SQLite, поставщиков, модельной маршрутизации и жизненного цикла Preview требуют обновления связанных разделов [документации](docs/README.md) в том же PR. Описывайте отдельно текущие факты исходников, результаты тестов и проектные планы. Датированные отчёты не переписывайте задним числом.
