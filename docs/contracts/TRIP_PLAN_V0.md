# TripPlan v0

**Фиксированный MOCK-пример; ограниченный OFFLINE HTTP+UI demo-путь.**

Документ [`trip_plan_v0.json`](trip_plan_v0.json) — один демонстрационный пример поездки. UI может загрузить его как статический MOCK или через `GET /api/trip_plan/demo`; это не расчёт API по текущей сессии. Поля сессии `experimental/app.py` этой схемой не меняются; корзины и заказы хранятся отдельно. `source_mode: MOCK` значит учебную цену, а не поиск рейса и не бронь.

Пример: Москва → Дубай, 12–19 ноября 2026, 2 взрослых и ребёнок 4 лет.

```text
54 000.00 ₽ перелёт + 81 000.00 ₽ отель + 5 500.00 ₽ трансфер = 140 500.00 ₽
```

Страховка в примере есть четвёртой строкой, но цена неизвестна: `amount` равен `null`, в `warnings` есть `PRICE_UNKNOWN`. Неизвестный компонент не прибавляется как ноль и не подменяется другим тарифом.

## Поля

Деньги записаны строкой с двумя знаками (`"54000.00"`), чтобы сумма не зависела от двоичной дроби. Неизвестная сумма — JSON `null`, не `"0.00"`.

| Поле | Тип | Обязательно | Что означает |
|---|---|---|---|
| `trip_id` | string | да | Идентификатор этого описания поездки. Это не `sid`, не `preview_id` и не `draft_id`. |
| `revision` | integer ≥ 0 | да | Номер уже сохранённой ревизии, с которой собран документ. См. ниже. |
| `travellers` | object | да | Состав группы. |
| `travellers.adults` | integer | да | Число взрослых. В примере: `2`. |
| `travellers.children` | array of integer | да | Возраста детей. Пустой массив, если детей нет. В примере: `[4]`. |
| `origin` | string | да | Город выезда. |
| `destination` | string | да | Город назначения. |
| `start_date` | string `YYYY-MM-DD` | да | Первый день поездки. |
| `end_date` | string `YYYY-MM-DD` | да | Последний день поездки. |
| `currency` | string | да | Валюта итога, код ISO 4217. Компоненты в другой валюте в эту сумму не складываются. |
| `budget` | object | да | Указанный пользователем лимит, отдельно от рассчитанной стоимости. |
| `budget.amount` | decimal string или `null` | да | `null`, если лимит не задан; никогда не подставлять лимит по умолчанию. |
| `budget.currency` | string | да | Валюта лимита; должна быть сопоставима с проверяемой стоимостью. |
| `budget.scope` | `whole_trip`, `hotel_only`, `unspecified` | да | На что именно распространяется ограничение. Для неизвестного лимита обязательно `unspecified`. |
| `hotel` | object | да | Жильё. |
| `hotel.name` | string | нет | Подпись для карточки. |
| `hotel.checkin` | string `YYYY-MM-DD` | да | Заезд. |
| `hotel.checkout` | string `YYYY-MM-DD` | да | Выезд. |
| `hotel.amount` | decimal string или `null` | да | Цена жилья в основных единицах валюты. `null`, если цена неизвестна. |
| `hotel.currency` | string | да | Валюта этой строки. |
| `hotel.source_mode` | string | да | Сегодня в примере только `MOCK`. |
| `hotel.provider` | string | да | Имя источника строки. `mock-hotel` не является живым поставщиком. |
| `transport` | object | да | Перелёт одной суммой за оба плеча. |
| `transport.kind` | string | да | В примере: `flight`. |
| `transport.departure_at` | string date-time | да | Вылет туда, ISO-8601 со смещением (`2026-11-12T10:00:00+03:00`). |
| `transport.arrival_at` | string date-time | да | Прилёт туда, ISO-8601 со смещением. |
| `transport.return_departure_at` | string date-time | нет | Вылет обратно. Для карточки «12–19» предлагается держать его рядом с туда. |
| `transport.return_arrival_at` | string date-time | нет | Прилёт обратно, ISO-8601 со смещением. |
| `transport.amount` | decimal string или `null` | да | Цена перелёта. `null`, если тариф неизвестен. |
| `transport.currency` | string | да | Валюта перелёта. |
| `transport.source_mode` | string | да | В примере: `MOCK`. |
| `transport.provider` | string | да | В примере: `mock-air`. |
| `transfer` | object | да | Трансфер. |
| `transfer.kind` | string | нет | В примере: `airport_hotel`. |
| `transfer.fare_scope` | string | да | Для данного примера `one_way_arrival`, то есть трансфер только из аэропорта в отель, не обратно. |
| `transfer.duration_minutes` | integer или `null` | да | Продолжительность поездки; `null`, если неизвестна. |
| `transfer.pickup_at` | date-time со смещением или `null` | да | Время подачи машины; `null`, если неизвестно. |
| `transfer.amount` | decimal string или `null` | да | Цена трансфера. `null`, если неизвестна. |
| `transfer.currency` | string | да | Валюта трансфера. |
| `transfer.source_mode` | string | да | В примере: `MOCK`. |
| `transfer.provider` | string | да | В примере: `mock-transfer`. |
| `insurance` | object | нет | Четвёртая платная строка, если страховка показана отдельно. |
| `insurance.amount` | decimal string или `null` | да, если объект есть | Известная цена. `null`, если цены нет. |
| `insurance.currency` | string | да, если объект есть | Валюта строки. |
| `insurance.source_mode` | string | да, если объект есть | В примере: `MOCK`. |
| `insurance.provider` | string | да, если объект есть | В примере: `mock-insurance`. |
| `insurance.fare_status` | string | да, если `amount` равен `null` | `UNKNOWN`: строка не является доступным тарифом. |
| `total_amount` | decimal string или `null` | да | Сумма известных строк в `currency`. `null`, если итог назвать нельзя. |
| `warnings` | array | да | Предупреждения. Пустой массив допустим, только если все показанные цены известны. |
| `warnings[].code` | string | да | Код. Для неизвестной цены: `PRICE_UNKNOWN`. |
| `warnings[].component` | string | да | Какая строка затронута: `hotel`, `transport`, `transfer` или `insurance`. |
| `warnings[].message` | string | да | Короткий текст для человека. |

Обязательные платные строки поездки: `hotel`, `transport`, `transfer`. Если у любой из них `amount` равен `null`, `total_amount` тоже `null`: частичная сумма не выдаётся за полную цену поездки. Необязательная строка (`insurance`) с `amount: null` в сумму не входит и обязана иметь предупреждение.

## Ограничение бюджета и неполные расходы

`budget` — отдельный объект, а не другое название `total_amount`. Когда пользователь говорит «80 000 ₽ на всю поездку», `budget.scope=whole_trip`. Если ограничение только для гостиницы, `scope=hotel_only`. Если область не понятна, требуется уточнение; модель не должна молча выбирать `hotel_only`.

- `whole_trip`: сопоставить лимит с `total_amount` только при известных обязательных компонентах и согласованной валюте.
- `hotel_only`: сравнивать с `hotel.amount`, не путать его с полной стоимостью поездки.
- `unspecified` плюс `amount:null`: лимит не задан и превышение не определено. Демо-файл не выдумывает бюджет пользователя.
- Если обязательная цена неизвестна, результат сравнения с общим бюджетом тоже неизвестен. Нельзя трактовать частичную сумму как экономию.

`transfer.fare_scope=one_way_arrival` относится только к прибытию из аэропорта в отель. Обратный трансфер не включён и не считается нулевым. `duration_minutes:null` и `pickup_at:null` означают неизвестные значения, а не отсутствие нужной поездки. Прежде чем показывать полный all-in бюджет, проверить обе стороны трансфера либо пометить невключённые расходы.

## Как `revision` связан с сохранённым состоянием

Сейчас подтверждённая поездка хранит целое `revision` в состоянии сессии (`prototype/session.py`, `State.revision`, с нуля). Рядом живут другие идентификаторы, и эта схема их не заменяет:

- `sid` — сама сохранённая поездка;
- `preview_id` — конкретное предложение, которое ещё ждут подтвердить;
- `draft_id` — цепочка уточнений черновика;
- `revision` — номер уже записанной версии. Подтверждение с другим номером не применяется (`STALE_REVISION`).

`revision` в TripPlan — тот же номер: документ описывает поездку в той ревизии, которая уже сохранена. Пока ревизия не сменилась, клиент может сослаться на неё при чтении. После успешного изменения номер в сохранённом состоянии увеличивается на 1. Старый документ с прежним `revision` к новой записи не относится.

В примере `revision` равен `0`, как у новой сессии до первого сохранённого изменения. Это значение демонстрации, не ответ текущего HTTP.

## Что происходит с тарифом после изменения дат

`checkin` и `checkout` уже входят в набор полей, при смене которых прежний результат источника нужно заново оценить (`source_refresh_required` в текущем `Session.preview`). Для этой схемы то же правило распространяется на `start_date`, `end_date` и на `departure_at` / `arrival_at`.

После смены дат:

1. Прежние `amount` у отеля, перелёта и трансфера больше не являются тарифом новых дат.
2. Пока новой цены нет, у затронутой строки `amount` становится `null`, а в `warnings` появляется `PRICE_UNKNOWN`. Ноль и «какой-нибудь доступный» тариф вместо неизвестной цены не подставляются.
3. Если неизвестна обязательная строка, `total_amount` тоже `null`.
4. Сохранённое изменение получает новый `revision`. Подтверждение старого предложения со старым номером не проходит.

`MOCK` в этом файле не обновляет тариф сам: это фиксированный пример для согласования полей.

## Граница проверки UI в PR #118 (26.10.2026)

JSON-контракт выше не меняется. В этой частичной интеграции локальный
`/trip_plan_demo.json` отдаётся как статический пример; `/api/trip_plan/demo` —
тоже демонстрационный источник, а не API расчёта по сессии.
Оба явно открываемых источника имеют клиентскую политику `fixed_demo`:
контроллер возвращает `status: demo`, `verification: FIXED_MOCK_DEMO`.
Даже совпадающие поля не делают этот документ персональной котировкой.
Отправление и бюджет сессии не сверяются для демонстрации; это явно написано
в статусе и самой карточке. Сравнение с бюджетом пользователя в ней отключено.
Проверки ревизии, назначения, дат, состава гостей и валюты сохранены.

Будущий согласованный источник по сессии должен быть явно подключён вызывающим
кодом с политикой `session` (`createController` / `mount`, параметр `sources`).
Его URL здесь не придумывается и в основной UI не добавлен. Для него обязательны
валидные поля плана и известный контекст: `origin`, `destination`, даты, гости,
валюта, ревизия и `budget.amount/currency/scope`. Все эти поля должны совпасть.
Отсутствующий бюджет или его поле — неизвестные данные; только явный объект
`{amount: null, currency: ..., scope: "unspecified"}` обозначает отсутствие лимита.
Указанная сумма с неизвестным scope не допускает проверки. Несовпадение отклоняется;
при неизвестном контексте возвращается `TRIP_PLAN_CONTEXT_UNKNOWN`, без новой цены.
`VERIFIED_CONTEXT` означает только совпадение полей с контекстом, не проверку
доступности, свежести тарифа, полноты услуг или фактический LIVE-поиск.

Текущий гостиничный запрос не гарантирует сохранённого `origin` или `budget_scope`.
UI передаёт отсутствующие поля как неизвестные и не извлекает отправление из
назначения или текста учебного примера. Лимит из сохранённого запроса передаётся
отдельно от стоимости. Разбиение гостей по номерам отсутствует в TripPlan v0:
сверяются общее число взрослых и набор возрастов детей. Preview/Commit меняет
условия существующим путём; полного пересчёта MOCK после этого нет.

## OFFLINE DEMO: корзина и заказ (26.10.2026)

Путь в основном UI: «Пример полного маршрута» → отправить запрос → подтвердить
Preview → явно открыть серверный или локальный MOCK → «Сохранить DEMO-корзину» →
«Создать DEMO-заказ». Сохраняется один учебный заказ со стабильным `demo-...` ID,
`mode=DEMO_ONLY`, `payment_status=NOT_PROCESSED`, `booking_status=NOT_BOOKED`.
Деньги не списываются, ничего не бронируется. Оплата, карты и персональные данные
не запрашиваются. Preview/Commit остаётся существующим путём изменения условий.

| POST | Точные поля JSON |
|---|---|
| `/api/cart/demo` | `sid`, `revision` |
| `/api/order/demo` | `sid`, `revision`, `cart_id`, `idempotency_key` |

Оба POST требуют прежние same-origin и `X-TravelTech-Nonce` проверки,
`Content-Type: application/json`, `X-Request-ID`. Сервер проверяет владельца по
`session_owners`, читает сессию только из SQLite, сверяет её текущую ревизию и
отсутствие действующего PENDING Preview. Клиентская ревизия — только условие
сравнения. Отсутствующий sid, чужая или неизвестная сессия, лишние поля,
подставленный cart_id, план, сумма, владелец или source_mode отклоняются.
Перед повторной выдачей HTTP-ответа проверки выполняются снова: старый request
ID не обходит stale/pending-проверку.

Область узкая: только OFFLINE-сервер, сохранённый `source_mode=archive`, ревизия
0 и условия фиксированного примера (назначение Dubai/Дубай, AE; 12–19 ноября
2026; 2 взрослых и ребёнок 4 лет; RUB). Число взрослых и возраста детей
суммируются по номерам; размещение по номерам TripPlan v0 не подтверждает.
Любая новая ревизия блокирует путь, даже если изменён только бюджет.
Отправление и область бюджета гостиничной сессии не гарантированы: ответ и UI
сохраняют `FIXED_MOCK_DEMO`, явно сообщают об отсутствии персонального расчёта
и не выдают вердикт о бюджете. Рейс, доступность, страховка, обратный трансфер
и полный all-in бюджет не проверяются. Неизвестные суммы сохраняются как `null`;
если неизвестна обязательная строка, итог тоже `null`.

Сервер собирает канонический план сам и создаёт неизменяемый CartSnapshot.
Cart ID детерминированно связан с owner+sid+revision. MockOrderStore лежит в
`<storage>/mock_orders.sqlite` (WAL, synchronous=FULL), рядом со `state.sqlite`.
В Docker это `/app/runtime/mock_orders.sqlite`, покрытый существующим volume
`traveltech_data:/app/runtime`; без сохранения volume сохранность не обещается.

Во время проверки сессии и записи корзины/заказа удерживаются application lock
и `BEGIN IMMEDIATE` на state.sqlite. Конкурентная запись условий не проходит
между проверкой ревизии и локальной записью. MockOrderStore отдельной
SQLite-транзакцией атомарно сохраняет заказ и его receipt, с UNIQUE по
owner+cart+revision. Тот же ключ возвращает прежний заказ; новый ключ для этой
корзины тоже не создаёт второй заказ. HTTP-журнал и metadata используются, но
его COMMIT и COMMIT MockOrderStore не являются одной общей транзакцией.
После аварии в этом промежутке заказ может уже существовать, а HTTP-ответ — ещё
нет. Неожиданная ошибка помечает `state_changed=UNKNOWN`; повтор с тем же
cart/key безопасно восстанавливает результат, если сессия всё ещё допустима.
Внешних эффектов и платёжного запроса здесь нет.

UI сохраняет idempotency key в localStorage по серверному cart_id до POST заказа,
блокирует двойной клик и действия при pending/stale/busy. После перезагрузки
нужно снова явно открыть MOCK и корзину; повтор вернёт прежний ID. При недоступном
хранилище ключа POST заказа не отправляется. Потеря nonce лишает доступа к старому
заказу; восстановление владения и отдельный архив заказов не добавлены.

Проверки: `python -X utf8 scripts/check_local.py --suite quick` включает HTTP
demo-тесты; `node --test tests/demo_journey_ui.test.cjs` проверяет ключи, двойной
клик и поздние ответы. `tests/test_trip_plan_ui_browser.py` проверяет реальные
локальные HTTP endpoints в Edge на 1365 и 390 px вместе с Preview/cancel/commit,
перезагрузкой, stale-блокировкой и отсутствием внешних запросов. Docker-сборка и
перезапуск самого контейнера в этой задаче не запускались; проверены файловый
путь volume и перезапуск приложения с тем же storage.
